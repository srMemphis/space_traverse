# Research: C++ test framework for space_traverse

Ticket: [#4](https://github.com/srMemphis/space_traverse/issues/4) (map [#3](https://github.com/srMemphis/space_traverse/issues/3)).
Researched 2026-10-10 against official repos, release pages, docs and source code at the tags named below.

**Constraints from the map:** Windows / MSVC v145 (VS 2026), C++20, x64 only. Dependencies are vendored under `space_traverse/include/` with no package manager. The build is moving to premake5, so there is no CMake. The tests need `double` and `Eigen::Vector3d` comparisons with tolerance; the vendored Eigen is **3.4.0** (`space_traverse/include/Eigen/src/Core/util/Macros.h`).

## Recommendation

**Use doctest (v2.5.3), vendored as the single header `doctest/doctest.h`.** Add a small project-local helper header for tolerant `double` and `Eigen::Vector3d` checks.

- It is the only one of the three that is still truly header-only, so premake needs nothing beyond an include path and one `DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN` translation unit. There is no compiled third-party library and no CMake-generated config.
- It has the lowest compile cost of the three, per its benchmarks.
- `doctest::Approx` is enough for scalars. We need our own Vector3d helper whichever framework we pick, unless we take on gMock.
- Its assertions are thread-safe, which helps code that runs under OpenMP.
- It is actively maintained again: four releases in 2026, and CI on VS 2026.

The cost: Test Explorer integration relies on a third-party pre-release VSIX. Without it, tests run as a console exe (`F5` / `Ctrl+F5`), which is fine for this project's size.

**Runner-up: GoogleTest (v1.18.0).** Choose it instead if built-in VS Test Explorer support matters more than everything else. You compile `gtest-all.cc` (plus `gmock-all.cc` for `Pointwise`/`DoubleNear`) as a static-lib project in premake and match the CRT setting. **Catch2 v3** has the best matchers, but it is the worst fit for a no-CMake vendored build. See below.

## Details

### Vendoring and premake

- **doctest.** The release ships `doctest/doctest.h` as one assembled header. The v2.5.x work splits the sources into `doctest/parts/`, but CI checks that the assembled header stays in sync with them [1][7]. Drop it into `space_traverse/include/doctest/`. In premake the test project needs only `includedirs` plus a `main.cpp` with `#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN`.
- **Catch2 v3.** The split library is configured at CMake time: `src/catch2/catch_user_config.hpp.in` is marked "AUTOGENERATED FROM CMAKE CONFIGURATION" and uses `#cmakedefine` [9]. Building it with premake therefore means maintaining that header by hand. The supported non-CMake path is `extras/catch_amalgamated.hpp` (561 KB) + `.cpp` (464 KB). Upstream says to expect worse compile times with it [5].
- **GoogleTest.** `src/gtest-all.cc` `#include`s every other source file, so a static-lib project can build from one TU [8]. By default it links the C runtime statically, while VS projects use the dynamic CRT. A mismatch gives LNK2038; the CMake option `gtest_force_shared_crt` fixes it, so in premake set `staticruntime` the same way in both projects [6]. Upstream recommends "building from the latest commit" over release branches [3], and its README announces a planned dependency on Abseil [6]. That would mean more to vendor later.

### Compile time

- doctest's own MSVC benchmark is old: doctest 2.2.0 against **Catch2 2.3.0**, on VS 2017. In it, header inclusion cost about 11 ms per TU for doctest against about 400 ms for Catch2. 50k `CHECK(a==b)` in Release took 58.7 s against 448.7 s [10]. **Treat these as directional only:** Catch2 v3 says it cut inclusion overhead by ~80% compared to v2 when used as a library, but the amalgamated build is slower than that [5]. No first-party benchmark covers GoogleTest on MSVC.
- For a few dozen unit tests, all three are acceptable. doctest keeps the test project cheapest to iterate on.

### Floating point and `Eigen::Vector3d`

- **doctest `Approx`.** It passes if `|a-b| < eps * (scale + max(|a|,|b|))`, with default `eps = 100*FLT_EPSILON ≈ 1.19e-5` and `scale = 1.0` [7] (`doctest.h` around line 6556). **Gotcha for this project:** the default `scale = 1` adds an *absolute* floor of ~1.2e-5. SI quantities such as charge per element (~1e-15 C), lengths in m and times in s would therefore pass against almost anything. Tests on small SI magnitudes must use `.scale(0)` (purely relative) or an explicit absolute tolerance. This belongs in the test-conventions decision.
- **Catch2.** `WithinAbs`/`WithinRel` are clearly specified and composable with `||` [12]. `Approx` defaults to `margin = 0, scale = 0`, so it is purely relative, but the docs discourage it for new code [12]. `RangeEquals(range, predicate)` takes a custom element comparator [14].
- **GoogleTest.** `EXPECT_NEAR` is absolute-only and `EXPECT_DOUBLE_EQ` is 4 ULP [13]. `Pointwise(DoubleNear(tol), v)` needs **gMock** [15].
- **Eigen 3.4 specifics.** `begin()`/`end()` exist for vectors only. For 2D matrices `iterator`/`const_iterator` are `void` (`DenseBase.h` lines 634–652). So Vector3d works as a range in Catch2/gMock matchers, but `Matrix3d` does not. GoogleTest's `IsContainerTest` SFINAE needs `++iterator`, so Matrix3d safely falls back to `operator<<` [18]. Catch2 prefers `operator<<` over range printing when it exists [17]. No relevant Eigen-related bugs turned up in any of the three trackers.
- **Conclusion.** With any framework, the cleanest approach is a project helper, e.g. `tests/support/approx.h`, built on `doctest::Approx` (or the framework's matcher). It should offer `CHECK_VEC_NEAR(actual, expected, absTol, relTol)` that compares per component and prints both vectors with `INFO`. Eigen's `isApprox` alone is a poor assertion: it is a norm-relative check, and a failure doesn't show the values.

### Visual Studio Test Explorer on VS 2026

- **GoogleTest.** Microsoft's docs list Google Test among the frameworks included "with no extra downloads required". The Test Adapter for Google Test is a default component of the *Desktop development with C++* workload [24]. It discovers executables by a configurable regex or a `<exe>.is_google_test` marker file, and runs them with `--gtest_list_tests` [25].
- **Catch2.** "Test Adapter for Catch2" by Johnny Hendriks supports Catch2 2.x and 3.x and needs a `.runsettings` file before it discovers tests. Its last commit was 2023-12 [23]. The manifest declares `[17.0, 18.0)`.
- **doctest.** "Test Adapter for Doctest" (comfyjase) is open source, built on vstest, and supports discover/run/debug. It is still pre-release 0.2.3, last updated 2025-11, and its manifest declares VS 2022 `[17.0,18.0)` [22].
- **Third-party VSIXs on VS 2026.** VS 2026 checks only the *lower* bound of a VSIX's install range and ignores the upper bound. The docs give `[17.0,18.0)` as an example that "runs in both Visual Studio 2022 and Visual Studio 2026" [26]. Both adapters should therefore install on VS 2026, but neither author documents testing on it. **This is unverified; check it locally before relying on it.**
- **Without an adapter:** each framework produces a console exe. `F5` on the test project shows failures in the console. doctest breaks into an attached debugger on a failed assertion by default; Catch2 does so with `--break`. That is enough for a project with no CI (CI is out of scope in #3).

### Maintenance

- **doctest.** It had no release between v2.4.11 (2023-03) and v2.4.12 (2025-04), then v2.5.0–2.5.3 came out between 2026-03 and 2026-07. A new maintainer group (`mitchgrout` and others) is active, and the `dev` branch was committed to on 2026-08-29. v2.5.3 moved CI to "Visual Studio 18 2026" [1].
- **Catch2.** It is the most actively released of the three: at least eight releases in 2026 (v3.13.0 to v3.16.1), the latest on 2026-10-08 [2].
- **GoogleTest.** It follows "live at head" with occasional release branches; v1.18.0 came out in 2026-08 and requires C++17 [3]. Google's backing makes it very safe long-term.

### Other options considered

- **boost-ext/ut** is a C++20, macro-free single header that lists MSVC 2019+ among its tested compilers [27]. Its last release was v2.3.1 (2025-04). It has no VS Test Explorer adapter, and it leans heavily on C++20 features where MSVC has historically lagged. Not worth the risk here.
- **Microsoft Native Unit Test Framework** (`CppUnitTestFramework`) has first-class Test Explorer support [24]. However, it ships with VS rather than as vendorable source, ties the tests to MSVC and VS, and builds the tests as a DLL. That works against the "keep cross-platform in mind" note in #3.

## Open questions for the test-conventions decision

1. Default tolerances: a relative epsilon for computed physics quantities and an absolute epsilon for geometry in metres. Avoid doctest's default `scale = 1` for SI magnitudes.
2. Whether the Test Explorer adapter is wanted at all, or whether "F5 the test project" is the workflow.
